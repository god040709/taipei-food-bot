# Taipei Food Bot 台北餐廳推薦聊天機器人

用聊天的方式找台北的餐廳：輸入「我們三個人想在信義吃麻辣鍋 一人一千」，系統會解析出地區、料理類型、人數和預算，並推薦最合適的 5 家餐廳。

## 系統架構

```
使用者在 Open WebUI 輸入需求
        │
openwebui_pipe.py      只負責轉送（約 130 行，貼一次就不用再改）
        │  POST /chat                     ▲ 需要 LLM 時，API 回「請幫我問這個」，
        │                                 │ pipe 用 Open WebUI 裡設定的金鑰去問，再把答案送回 API
api.py                 機器人 API（預設 port 5000）
        │
src/bot.py             對話流程：理解需求 → 反問／排除／換一批 → 查餐廳 → 組合回覆
src/lexicon.py         詞庫與提示詞（地區、類別、子類型、地標、同音錯字）
src/recommender.py     篩選 → 計算推薦指數 → 取前 5 名
        │
data/taipei_all_restaurants.csv   台北 12 區 × 14 類，約 2,900 家餐廳
        ▲
collector_taipei.py    從 Google Places API (New) 採集資料
```

**API 不保存、也不使用任何 LLM 金鑰。**金鑰只填在 Open WebUI 的函式設定裡，別人就算連到你的 API，也用不到你的 LLM 額度。每個人都在自己的環境架一份，用自己的金鑰。

## 快速開始

### 1. 安裝套件

```bash
pip install -r requirements.txt
```

Windows 若找不到 `pip`，改用 `python -m pip install -r requirements.txt`。

### 2. 啟動推薦 API

**在自己電腦：**

```bash
python api.py
```

看到 `Running on http://127.0.0.1:5000` 即成功，視窗保持開著。

**在實驗室平台（lab-30-docker）：**

```bash
source /opt/venv_torch/bin/activate
cd ~/projects/taipei-food-bot
nohup env HOST=0.0.0.0 python api.py > api.log 2>&1 &
```

`HOST=0.0.0.0` 讓 Open WebUI 容器連得到；`nohup` 讓 API 在背景持續執行。

測試 API 是否正常（會回一則反問或推薦）：

```bash
curl -s -X POST localhost:5000/chat -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"大安燒肉 2人 800"}]}'
```

### 3. 在 Open WebUI 加入 Pipe（只要做一次）

1. 左下角頭像 → **管理員控制台** → **函式** → **建立**
2. 貼上 `openwebui_pipe.py` 的完整內容，填寫名稱與 ID 後儲存，並打開開關
3. 點函式右邊的**齒輪**設定：

| 設定 | 自己電腦 | 實驗室平台 |
|---|---|---|
| Api Url | 預設即可（`http://127.0.0.1:5000/chat`） | `http://testbed:5000/chat` |
| Llm Api Key | 選填 | **自己的** `LLM_API_KEY`（實驗室 `.env` 裡） |
| Llm Model | 選填 | `Qwen3.6-35B-A3B`（以管理者提供的名稱為準；留空會自動用服務上的第一個模型） |

4. 新增對話，模型選這個 Pipe，輸入「大安燒肉 兩個人 預算800」測試

> 舊版設定的 Api Url 是 `…/recommend`，新版 pipe 會自動改用 `…/chat`，不用另外改。

### 4. 更新到最新版

機器人的邏輯都在 API，**更新時不用重貼 pipe**：

```bash
git pull
pkill -f api.py; nohup env HOST=0.0.0.0 python api.py > api.log 2>&1 &
```

只有 `openwebui_pipe.py` 本身有改動時（很少發生），才需要重新貼到 Open WebUI。

## 推薦邏輯

### 需求解析

- **LLM 解析**（在齒輪填入 LLM 金鑰後啟用，主要的方式）：理解自由的句子、多輪對話（「再便宜一點」）、意圖（找店／換一批／不喜歡／閒聊／全新的需求），以及其他條件（附近、不要連鎖、隱藏版…）。使用伺服器的 JSON 格式功能，保證回傳的欄位正確
- **規則解析**（備案，不需要金鑰）：地區、類別、人數、預算、第幾間、同音錯字、捷運站、預算區間、不要某類別。LLM 掛掉或漏填某個欄位時，用規則補上

回答第一行會顯示解析出的條件，以及使用哪種解析方式。

**推薦過之後**：條件行上寫「不限」的項目（例如「不限類別｜人數不限」）算已經回答過，之後追問或修改都不會再問。「有哪些類型可以選」有 LLM 時由 LLM 判斷（「不管是什麼類型」不會被誤判成在問類型清單）。

**新需求和修改**：推薦完之後，如果使用者重新講了完整的條件（一次講 3 項以上，或 LLM 判斷是全新的需求），之前的其他條件（附近、隱藏版、不要的類別、預算下限）不再套用，並顯示「🆕 這是新的需求…」；「不要連鎖」會保留；不喜歡過的店不再排除，並在同一行說明（還是不想去可以再說）。只改一兩項（「換成燒肉」）則沿用其他條件。

### 資訊不足時持續反問

機器人需要知道 **地區、類型、人數、每人預算上限** 四項，缺哪一項就問哪一項，使用者回答後合併條件，直到四項都清楚才推薦。

- 某一項不在意：「地區都可以」「預算不限」→ 那一項不再問
- 全部不在意：「都可以」「隨便」→ 直接用目前的條件推薦
- 同一個需求最多反問 4 次（齒輪的 `Max Ask`），避免一直問不完；齒輪的 `Ask Followup` 可以關閉反問

### 總預算、換一批、料理類型列表

- **總預算**：「總預算 1500」「總共 2000」「全部加起來 3000」會除以人數換算成每人預算；還不知道人數時會先問人數
- **換一批**：推薦完後說「推薦別的」「還有其他的嗎」「換一批」，會用同樣的條件、排除已經推薦過的店再推薦 5 家；都推薦完了會建議放寬條件
- **同品牌的分店**（品牌從店名推測，跟判斷連鎖店的方法一樣）：同一批只留一家，有捷運站／地標時留最近的，沒有時留評分可信度最高的；推薦過的品牌，換一批時也不會換成它的其他分店。條件改了（例如改說公館附近）會重新挑
- **料理類型列表**：問「有什麼類型可以選」「有哪些料理」，會列出各類型和店家數（依目前的地區、預算計算），回覆類型就能接著推薦

### 子類型（壽喜燒、麻辣鍋、壽司、牛排…）

資料集只有 14 個大類，「壽喜燒」「麻辣鍋」都被分在「火鍋」。說出子類型時（設定在 `src/lexicon.py` 的 `SUBTYPES`，約 45 種）：

- **店名看得出是這種的店排最前面**（從店名關鍵字判斷，例如店名有「麻辣」→ 麻辣鍋），就算比預算稍微高一點也一樣；其他同類別的店排在後面，中間有「🍽️ 以下是一般的火鍋店」分隔
- 部分子類型會跨類別找，例如被分在「燒肉」的壽喜燒店也會被找到
- **這一區找不到**：誠實說明，並告訴使用者全台北有幾家（「想看可以說『不限地區』」）
- **整個資料庫都沒有**（例如羊肉爐、薑母鴨）：不直接列一般的店，而是先反問要改成一般火鍋，還是資料裡有的其他子類型（附家數）
- 限制：只看店名，店名沒寫的（例如「無老鍋」）判斷不出來；要更準確需要另外用子類型關鍵字重新採集資料

### 不喜歡／吃過、閒聊

- 「我不喜歡第 2 間」「肉老大吃過了」「這些都吃過了」→ 之後都不再推薦那些店**和同品牌的其他分店**（換地區、換類型也一樣，提出全新的需求才清掉），並補上新的選擇；只說「吃過了」時會反問是哪一間
- 有 LLM 時，「那間太遠了」這類比較口語的說法也能判斷
- **閒聊（有 LLM 時，任何時候都可以）**：「你會做什麼」、打招呼、道謝、問推薦過的店的細節、「你推薦哪一間？」，會由 LLM 用自己的話回覆並引導回找餐廳；跟吃飯無關的話會禮貌帶回來。能做的事寫在 `src/lexicon.py` 的 `CHAT_PROMPT`（只列事實、不給範例句，避免制式回答）。閒聊不會打斷正在進行的反問，也不會清掉已經說過的條件。沒有 LLM 時不處理閒聊
- **「你幫我挑一種料理」（有 LLM 時）**：機器人先問齊其他條件（反問裡會記下「🎲 料理類型交給我挑」），再從目前地區、預算下有店的類別隨機挑一種，顯示「🎲 幫你挑了『燒肉』」；說「換一種」會再挑一個不一樣的
- **換一批但保留某幾間**（「換一批，但第 1 間留著」）：保留的店排最前面，其他換新的；換掉的不會被永久排除
- **「最後一間」「倒數第 2 間」**：規則就認得
- **台北市以外的地點、14 類以外的料理**（板橋、越南菜…）：說明資料範圍，並建議附近的台北市區域或相近的類別
- **人數太多**（資料裡的店大多標示 10 人以內）：找不到時改成不限人數推薦，並提醒先確認座位或訂位
- **「重新開始」**：條件、不要連鎖、不喜歡過的店全部清掉（回覆最後會有「🔁 已重新開始」）
- **反問時說「不知道」**：不當成不限，改成給具體選項讓使用者挑
- **「預算再高一點」**：預算 ×1.3；「再便宜一點」×0.7
- **LLM 判斷「不限」**：只用在本來就不知道的欄位（避免把已經知道的條件清掉）
- **反問也由 LLM 用自然的話問**（缺條件、「是哪一間呢」、「資料庫沒有這種店」）：要問哪些項目由程式決定，LLM 只負責措辭；程式會檢查每一項都有問到，漏了就補一句。店名清單和選項家數由程式列出，避免寫錯。沒有 LLM 時用固定的範本
- 條件行會顯示 LLM 沒用上的原因，例如「（規則解析・未設定 LLM 金鑰）」「（規則解析・連不到 LLM 服務）」，方便檢查設定

### 其他條件（附近、連鎖、隱藏版…）

條件行下面的「🎛️ 其他條件：…」會被記住，下一句沿用；說「連鎖也可以」「有名的也可以」可以取消。

| 說法 | 做法 | 沒有 LLM 時 |
|---|---|---|
| 「忠孝復興附近」「捷運古亭站」「西門町」「台北101」 | 用經緯度找捷運站 **800 公尺內**的店（不限行政區），不到 5 家放寬到 1.5 公里；卡片顯示距離。跟行政區同名的站（大安、中山…）要說「站」或「捷運」 | ✅ |
| 「預算 500 到 1000」「1000 以上」 | 預算下限：多數人花費的上限要到這個金額 | ✅ |
| 「日式或韓式都可以」 | 多個類別，結果輪流排 | ✅ |
| 「剛吃過火鍋」「火鍋以外都可以」 | 排除這個類別 | ✅ |
| 「最貴的」「最便宜的」 | 依價格（多數人花費區間的中間值）由高到低或由低到高排，同價位再看推薦指數；不用再問預算 | ❌ |
| 強調重點：「越近越好」「評價最重要」「要有名的」 | 預算等級不變（預算內的店還是排前面），同一級裡依距離／評分可信度／評論數排。只取一個重點，改口以最新的為準。「越近越好」但沒說在哪：說明讀不到位置、請使用者給最近的捷運站；給不出來就照一般順序推薦 | ❌ |
| 放寬：「走遠一點沒關係」「貴一點沒差」 | 捷運站附近直接用 1.5 公里找；預算多 200 元來找（價格大多以 200 元為一級）。強調和放寬都不會改動使用者說的預算金額 | ❌ |
| 「不要連鎖店」 | 排除連鎖：同一個品牌名在資料裡有 2 家以上不同的店 | ❌ |
| 「比較沒人知道的」「隱藏版」「私房」 | 評分 4.3 以上、評論數至少 50 則、且少於同區同類型的中位數；排序不看人氣 | ❌ |
| 「要有包廂」「停車」「營業時間」「素食」「適合約會」… | 資料沒有這些欄位：誠實說明沒辦法篩選，請看 Google Maps | ❌ |

**同音錯字**：「大按→大安」「伙鍋→火鍋」「中孝復興→忠孝復興」「少肉→燒肉」「預酸→預算」會自動修正，並在條件行下顯示「✏️ 『大按』看成『大安』」。做法是比對讀音（不管聲調），至少要有一個字完全一樣、不改「是、的」這類常用字，也不改「美食」「大致」這種本身就是常用詞的字。拼音表存在 `data/lexicon_generated.json`，虛擬機和 Open WebUI 不用安裝套件。有 LLM 時也會請 LLM 依讀音判斷。

修改 `src/lexicon.py` 的地區、類別、子類型或地標清單後，重新產生拼音表：

```bash
pip install pypinyin
python tools/build_lookups.py                           # 只更新拼音表
python tools/build_lookups.py northern-taiwan.geojson   # 連捷運站座標一起更新
```

（車站資料：[repeat/northern-taiwan-metro-stations](https://github.com/repeat/northern-taiwan-metro-stations) 的 `output/northern-taiwan.geojson`）

### 預算是「每人上限」

資料中的價格區間是 Google 的「**多數人用餐的每人花費**」，不是最低／最高消費。

- 優先推薦**多數人的花費都在預算內**的店（區間上限 ≤ 預算）
- 接著是預算落在花費區間中間的店（例如預算 300、多數人花 $200–$400），標示 ⚠️ 可能超出預算
- 符合預算的店不到 5 家時，預算依序放寬到 1.2 倍、1.5 倍、2 倍，把「比預算稍微高一點」的店放在 💸 分隔標題下面（越接近預算越前面）
- 花費區間下限就已經達到預算的店（例如預算 800、多數人花 $800–$1000）不算符合預算

### 推薦理由

每家餐廳都會附上 ✨ 推薦理由，寫這家店的特色和適合使用者的原因：

- 有填 LLM 金鑰：由 LLM 根據資料寫成自然的句子
- 沒有 LLM：列出資料中的事實（店名特色、同區同類型評論數排名、價格是否親民、是否在預算內）
- 執行過 `enrich_features.py` 後，LLM 還能參考 Google 的店家簡介、服務特色（可訂位、提供素食…）與顧客評論摘錄，寫出招牌菜、氣氛等特色

### 推薦指數（0～100）

| 項目 | 權重 | 說明 |
|---|---|---|
| 評分可信度 | 60% | 貝氏平均：評論數少的店，評分會被拉向整體平均，避免「5 則評論 4.9 分」排在「8,000 則評論 4.8 分」前面 |
| 人氣 | 25% | 評論數取 log 後正規化 |
| 預算吻合度 | 15% | 價格區間落在預算內的比例 |

權重可在 `src/recommender.py` 開頭調整。

> 規則解析是參考這 30 句測試題調整的，100% 偏樂觀。正式報告前，建議另外收集一批新句子再測一次。

## 補充餐廳特色（選用）

讓推薦理由能寫出招牌菜、氣氛等特色。需要 Google API 金鑰，會呼叫 Place Details，**執行前請先到 Google Cloud 確認價格與免費額度**。

```powershell
$env:GOOGLE_MAPS_API_KEY="你的金鑰"
python enrich_features.py
```

- 預設只抓每個「行政區 × 類別」推薦指數前 8 名（約 1,300 家），`$env:TOP_PER_GROUP="0"` 則抓全部
- 執行前會顯示要抓幾家並請你確認；中斷後重跑會跳過已抓過的店
- 結果存在 `data/restaurant_features.csv`，`api.py` 重新啟動後就會使用

## 重新採集資料（選用）

平常不需要執行。要更新餐廳資料時，需要自己的 Google API 金鑰（Google Cloud 啟用 **Places API (New)**，並將金鑰限制為只能使用此 API）。

```powershell
# Windows PowerShell
$env:GOOGLE_MAPS_API_KEY="你的金鑰"
python collector_taipei.py
```

```bash
# macOS / Linux
GOOGLE_MAPS_API_KEY=你的金鑰 python collector_taipei.py
```

抓不到資料時不會覆蓋原本的 CSV。

## 安全注意事項

- **不要把任何 API 金鑰寫進程式碼或 commit 到 GitHub**（本 repo 是公開的）。金鑰一律用環境變數或 Open WebUI 的齒輪設定
- LLM 金鑰只存在 Open WebUI；`api.py` 不會拿到金鑰，也不會自己呼叫 LLM
- 舊版程式碼曾包含一把 Google 金鑰，該金鑰已失效，請勿再使用
- `.gitignore` 已排除 `.env`、快取檔與壓縮檔
